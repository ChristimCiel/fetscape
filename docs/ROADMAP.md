# 接下來 30／90／180 天

這是分階段的軟體建議，不是工期或市場承諾。日數以決定啟動下一階段時計算；驗收未過，不因日曆到期而擴大宣稱。

## 30 天：驗證問題與計算基礎

**產品**：依最新 Fetscape 講稿，先集中 servicing／RPO 工程團隊的一個接近與退出驗證案例。公開軌道頁是幾何參考，機構頁是 authored concept；不以兩者替代 contact 或 GNC 驗證。

**技術**：請 orbital mechanics／SSA 專家檢查 time/frame、格式、失敗案例與搜尋策略。增加代表性歷史事件及獨立比較，建立變更時可重跑的 validation set。先把來源、更新與不確定度語意做對。

**Discovery 目標（假設，不是既有接觸）**：五次訪談、至少兩個 servicing／RPO 組織，涵蓋 mission／GNC 工程師與預算負責人。請對方帶實際匿名工作流與既有輸出，不只看 demo 給評語。

**通關證據**：至少一個重複出現的具體工作負擔、有可使用資料的 design partner、可被獨立重現的計算。若現有工具已充分解決痛點，應縮小或停止這個切入點。

## 60–90 天：一個授權案例與 pilot 驗收

與一個合作方定義 read-only pilot：使用哪種合法提供的資料、誰提供 reference truth、哪些結果只是來源轉呈、哪些是自行計算、怎樣算改善。

優先開發經 partner 要求的 **接近／推力退化 test-case 匯入與版本比較**、review 與 evidence 整合；若同一案例需要 CDM／operator ephemeris，再定義匯入與更新追蹤。這些格式尚未實作；不能把目前 GP importer 換個名稱當成支援。

CDM reader 先驗證 metadata、單位、frame、time 和 covariance 結構。來源提供的 Pc 與未來自行計算的 Pc 必須區分來源和版本；沒有通過專家與獨立案例驗證前不提供自己的 Pc。

依共同資料／部署需求加入認證、存取控制、資料隔離、retention、備份與 bounded worker jobs。避免未有需求就建多供應商、全 catalog、multi-tenant 平台。

**通關證據**：盲測歷史案例、量化工作流程基準、明確資料／存取責任，以及有預算負責人同意驗收條件的 pilot。尚未有付費承諾時，不把免費試用當成收入驗證。

## 90–180 天：付費 pilot 目標與重複使用

在合作方認可的邊界內完成付費 pilot，驗收科學結果、操作流程與可靠性；用實際使用頻率及付費理由決定商業化範圍。若需要營運通知，加入持續 ingest、job scheduler、狀態監控、投遞／失敗記錄，再談告警時效承諾。

只有 ADR 夥伴提出具體、可出資的任務問題，才擴展 B：共同 epoch 的初始狀態、相位／有限推力 transfer、獨立 GMAT／Orekit 等工具比較。近距感知、GNC、contact/capture、去旋與處置各有獨立驗證階段，不由介面動畫替代。

**通關證據**：付費、重複使用、驗收與資料取得方式可持續。否則重新選 ICP 或縮小產品，而不是靠增加功能掩蓋需求缺口。

## 最小團隊與投入

立即需要：Tim 負責產品／客戶與操作需求、一位能維護完整軟體資料流的工程人員，以及一位能實際審查計算與資料的 orbital mechanics／SSA 專家。增加 GNC／機構專業的時點，應對應到具體 ADR 能力。

在尚無 partner data 與驗收範圍前，不編造精確商業資料費、企業客戶預算或募資需求。下一階段估算應拆出工程人月、專家 review、資料授權、部署與安全成本，再用供應商／候選人報價建立 lean／base／ambitious 情境。此版使用的開源工具與公開快照不能代表 commercial pilot 的成本結構。

## Discovery 問題，一次帶齊

1. 最近一次 conjunction notice 是如何處理、由誰值班、最後產生什麼紀錄？
2. 哪個步驟最耗時、最常重做或容易誤解？目前工具如何解決？
3. 哪些資料能提供給 pilot、限制與授權是什麼？
4. 什麼 benchmark 足以讓團隊信任這個工具？誰負責驗收？
5. 誰能批准預算、從哪個預算購買、何時有採購窗口？
6. 如果 pilot 達到驗收條件，願意簽什麼具體付費安排？
